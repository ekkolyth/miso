# Script Resolution

Understanding how Miso resolves commands is important for organizing your scripts and avoiding conflicts. This page explains the resolution order and priority.

## Resolution Order

When you run a command with Miso, it resolves the command in the following order:

1. **Core built-in commands** — core Miso functionality
2. **Scripts folder** — custom scripts in your configured scripts directory
3. **Package-management commands** — commands to manage dependencies
4. **package.json scripts** — scripts defined in package.json
5. **Passthrough** — forwarded to the package manager

Let's examine each step in detail.

> In [simple mode](/working-with-miso/simple-mode) (`"packageManager": false`), steps 3–5 are dropped — Miso resolves core commands and folder scripts only, and ignores `package.json` entirely.

### 1. Core Built-In Commands

Miso starts with its core commands. These always win over a same-named script in your scripts folder:

- `init` — initialize a new project
- `version` — display the Miso version
- `env` — validate environment variables from `.env` files
- `scripts` — list available scripts and actions
- `skills` — add miso skills

The package-management verbs (`install`, `add`, `remove`, `run`, `dev`) and `upgrade` work the other way around: a folder script sharing one of those names runs instead of the built-in, so you can shadow them when you need to.

### 2. Scripts Folder

After the core commands, Miso searches your configured scripts folder recursively and runs the match:

```
scripts/
  build.sh       → miso build
  test.py        → miso test
  deploy/
    staging.sh   → miso deploy/staging
```

A file is discovered if it has executable permissions or a recognized extension (`.sh`, `.ts`, `.py`, and the rest — see [Script Execution](/scripting/script-execution#changing-the-interpreter)); files starting with `.` or `_` are skipped. The extension is optional when you invoke it, and an `index` file is a directory's default — `scripts/publish/index.sh` runs as `miso publish`.

If two scripts resolve to the same command name, Miso stops with an error instead of guessing which one you meant.

### 3. Package-Management Commands

If no script matches, Miso checks its package-management commands:

- `install` or `i` — install dependencies
- `add` — add new dependencies
- `remove` — remove dependencies

### 4. package.json Scripts

If nothing has matched yet, Miso looks for an entry in `package.json`:

```json
{
    "scripts": {
        "dev": "vite start",
        "build": "tsc && vite build",
        "lint": "eslint ."
    }
}
```

If a match is found, it runs via your configured package manager:

```bash
miso dev
# Executes: npm run dev (or bun dev, pnpm dev, etc)
```

A name defined in **both** your scripts folder and `package.json` is treated as ambiguous — Miso stops and asks you to rename one so the invocation is unambiguous, rather than quietly picking a winner.

### 5. Passthrough

If the command isn't found in any of the previous steps, Miso forwards it to your package manager:

```bash
miso outdated
# → forwarding "outdated" to pnpm
# Executes: pnpm outdated
```

This lets you use Miso as a unified interface for all package-manager commands without needing to remember which package manager you're using.

> Targeting specific workspaces with an `@scope` (e.g. `miso build @api`) is covered in [Monorepos](/scripting/monorepos#how-workspace-matching-works).
