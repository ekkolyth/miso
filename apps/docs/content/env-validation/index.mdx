# Env Validation

<Callout type="info">
> Miso automatically loads `.env` files into your scripts — you don't need `--env` for that. The `--env` flag and `miso env` are for **validation**: checking that variables exist and match their expected types before running.
</Callout>

## Usage

`miso env` validates environment variables from your `.env` files against rules defined in `miso.json`.

```bash
miso env
```

Or put `--env` before another command to validate before running it:

```bash
miso --env dev
miso --env build
```

Like `--ci`, `--env` only counts before the command. After the command it belongs to the tool, so `miso wrangler deploy --env production` passes `--env production` to wrangler.

## Quick Start

1. Add an `env` array to `miso.json`, with one entry per app or `.env` file. Each root entry needs a `scope` — a target name or `"global"`:

<Terminal
    copy={false}
    className="mt-4"
    title="miso.json"
    config={`{
\t"env": [
\t\t{
\t\t\t"scope": "web",
\t\t\t"label": "web",
\t\t\t"path": "apps/web/.env.local",
\t\t\t"variables": {
\t\t\t\t"PORT": "port",
\t\t\t\t"DATABASE_URL": "url"
\t\t\t}
\t\t},
\t\t{
\t\t\t"scope": "api",
\t\t\t"label": "api",
\t\t\t"path": "apps/api/.env",
\t\t\t"variables": {
\t\t\t\t"REDIS_URL": {
\t\t\t\t\t"type": "url",
\t\t\t\t\t"schemes": ["redis", "rediss"]
\t\t\t\t}
\t\t\t}
\t\t}
\t]
}`}
/>

2. Run `miso env` before starting your app (or in CI):

```bash
miso env && miso dev
```

Each entry is validated independently, and every failure is reported in one pass — grouped under its label, one variable per line:

```
  api
    REDIS_URL: missing required variable
```

## What gets checked

`miso env` and `--env` read the root `miso.json` **and** every workspace member's `miso.json`, in every repo mode. A clean exit means the whole repo's declared variables are present and well-typed — that's what makes it usable as a CI gate.

Two consequences worth knowing:

- **A member `miso.json` that won't parse fails the run.** Skipping it would report a pass over requirements nothing checked, which is the failure mode the gate exists to prevent.

    ```
    ERROR miso: load apps/web/miso.json: parse config: …
    ```

- **Members come from workspaces and `miso.json` files.** Members are the directories matched by `package.json` workspaces or `pnpm-workspace.yaml`, plus directories with their own `miso.json` at `*/` or `*/*/`. A workspace `!` exclusion wins, so an excluded directory isn't traversed.

## CI mode

A clean checkout usually has no `.env.local`. In CI mode, miso skips env files that aren't there instead of failing, so `miso format`, `miso lint`, and other commands that don't need your app's config still run.

CI mode turns on automatically when the `CI` environment variable is set, which GitHub Actions, GitLab CI, and CircleCI all do. To turn it on yourself, put `--ci` before the command:

```bash
miso --ci format @web
```

`--ci` only counts before the command. Anything after the command goes to the tool, so `miso test --ci` still passes `--ci` to Jest.

In CI mode:

- Env files that exist are still loaded. Missing ones are skipped.
- `miso env` and `--env` check each declared variable against the file, if it's there, and against the shell environment. A CI secret satisfies the schema without a `.env` file:

```bash
AUTH0_SECRET=${{ secrets.AUTH0_SECRET }} miso env
```

- A variable that's in neither place still fails validation.

## Auto-Discovery

Even without an `env` block in `miso.json`, Miso automatically loads a `.env` file into every script it runs. It walks the following candidates in order and loads the first one it finds:

| Priority | File               |
| -------- | ------------------ |
| 1        | `.env.local`       |
| 2        | `.env.production`  |
| 3        | `.env.development` |
| 4        | `.env`             |

Variables already set in the shell environment take precedence over values in the file — Miso never overrides a variable that is already present in the process environment.

In a monorepo, auto-discovery searches that member's own directory rather than the project root when you run a workspace-scoped script.

Discovered files follow the same expansion rules as a declared `path` (see [Configuration](/env-validation/config#path)), and a file that fails to parse stops the run.

## Scope & Resolution

Once you add an `env` block, each root entry needs a `scope` — a target name or `"global"` — so miso knows which command it applies to. Resolving the env for a run target layers global entries, then either the entries scoped to that target or (for a member declaring its own env) the member's `<member>/miso.json` entries, later winning on key conflict. The result still yields to anything already set in your shell. A given scope lives in the root config or the member's, never both — declaring it twice is an error.

`miso env` enforces `scope` strictly and fails on a missing one; loading env into a running script is permissive and just skips entries that don't match. In a delegated repo (`repo: "turbo"`/`"nx"`) the delegate resolves targets, so root entries don't need a `scope` there — but validation still traverses every workspace member's schema, and miso injects env for any task a `repo.tasks` override hands it to run. See [Configure](/env-validation/config#scope) for the full breakdown.
